## Bugs found

### BUG-1 (NEW): Admin `useCreateToolGrant` body shape mismatches API schema
- Where: `admin/src/facades/tool-grants/hooks.ts:90-109` builds
  `{ state?, config?, roleId?, agentId? }`, stripping `toolRegistryEntryId` into
  the URL.
- API expects (`api/src/routes/mcp.ts:114-120` `CreateGrantBodySchema`):
  `{ toolRegistryEntryId (uuid, REQUIRED), state?, config?, roleId?, agentId? }`.
- Result: every grant creation returns
  `{"error":{"code":"VALIDATION_ERROR","field":"body","details":{"fieldErrors":
  {"toolRegistryEntryId":["Required"]}}}}`. The AgentGrantMatrix is unusable.
- Reproduced live with a direct fetch from `browser_evaluate` using the same auth
  token — same 400.
- Severity: HIGH. Blocks the entire Slice E grant flow.
- Task creation: there is no `TaskCreate` MCP tool exposed to this verifier
  agent (ToolSearch on "TaskCreate"/"task create"/"planning" returned no matches).
  Filing the bug here in lieu; the orchestrator that owns the plan
  (`docs/plans/2026-05-16-mcp-universal-connector.md`) should pick this up.
- Suggested fix: pick ONE source of truth. Easiest is to include
  `toolRegistryEntryId` in the body alongside the URL param (cheap server-side fix
  is to drop the requirement and read from `request.params`).

### BUG-2 (NEW, lower): No reachable test MCP server for discovery in dev
- Where: the wizard happily accepts any URL but there is no local fixture MCP
  server bundled with the dev stack to validate `tools/list` discovery end-to-end.
- Impact on this task: cannot verify step 5 ("workflows/tools shows new
  server's tools") for an actually-installed MCP instance.
- Suggested fix: ship a tiny stdio/http MCP fake under `tools/` or
  `packages/mcp-client/test/` and expose it via `pnpm dev` so admins (and
  verifiers) can do an end-to-end smoke without leaving the box.

### BUG-2 RESOLVED (task #29)
- Fixture: `packages/mcp-client/test/fixtures/mcp-fixture-server.ts`. Pure
  Node built-ins (`node:http` + `node:crypto`), zero new dependencies, binds
  to `127.0.0.1:4318` only. Exposes `echo`, `now`, `fixture_add` over the
  Streamable-HTTP MCP transport (POST `/mcp`, JSON-RPC body in, JSON-RPC body
  out, `mcp-session-id` minted on `initialize`).
- How to start: `pnpm dev:mcp-fixture` (root) or
  `pnpm --filter @nessie/mcp-client start:fixture`. Override port with
  `pnpm --filter @nessie/mcp-client start:fixture -- --port 4319`.
- How to use from the admin: open `http://localhost:5555/mcp-app-store`,
  "Add MCP server" wizard → transport `http`, URL `http://127.0.0.1:4318/mcp`,
  name `local-fixture`, label `Local MCP Fixture`, auth method `none`. Click
  the new catalog entry → "Install" → scope `organization`. On the installed
  scope row click "Test & discover" — instance flips to `active`, health
  checked, 0 failures.
- E2E proof of discovery: `e2e/screenshots/2026-05-16-mcp-flow/post-fixture-discovery.png`
  shows `/workflows/tools` listing all three fixture tools (`echo`, `now`,
  `fixture_add`) as `mcp-remote` rows with status `pending review` alongside
  the existing builtins. End-to-end probe → projection → registry display
  verified.
- Curl smoke (with fixture running):
  ```
  curl -s -X POST http://127.0.0.1:4318/mcp \
    -H 'Content-Type: application/json' \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
  ```
  returns `{"jsonrpc":"2.0","id":1,"result":{"tools":[{...echo...},{...now...},{...fixture_add...}]}}`.
