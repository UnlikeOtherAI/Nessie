# File storage & accounting — single chokepoint

Authoritative standard. `AGENTS.md` → "File storage & accounting" carries the
one-line summary and points here; **this file is the rule.**

- **All blob file operations** — store, stream, download, delete, version — MUST go through the one `@nessie/runtime` `FileService` (`createFileService`). Never call `getStorage` / `storage.*` or `prisma.attachment` for file bytes from anywhere else (routes, worker tools, services). Build it once per process from `config.storage`. Attachment→message linking (`Attachment.messageId`) carries no bytes and no accounting delta, so it is not a `FileService` operation: it is an ordinary `prisma.attachment.updateMany` write, guarded by the message-visibility check on the target thread (see `api/src/routes/thread-message-create.ts`). Ticket linking (`Attachment.taskId`, and `Attachment.taskCommentId` for a comment's files) is the same kind of write, done by `linkUploadsToTask` in `@nessie/team-admin` (and by the board-source sync on a provider file it has just stored), which links the actor's own still-unlinked uploads (no `messageId`, `emailMessageId`, `knowledgePageId`, `taskId`, `taskCommentId` or `executorCommandId`) to a ticket the actor can read; `canAccessAttachment` answers a linked file by `executorCommandId`, `messageId`, `emailMessageId`, `taskId`, knowledge-page denial, uploader, or published asset, in that order. See [ticket-activity.md](ticket-activity.md).
- **An image a local program returns is a `FileService` file of its executor command.** The daemon uploads each image of an `mcp.call` result before the result's receipt (`POST /api/executor-daemon/commands/attachment`, [command-attachments.md](../executor-protocol/command-attachments.md): one JSON body of at most 4 MiB decoded, the one daemon route past the 1 MiB body limit), and `recordAuthorizedExecutorCommandAttachment` (`@nessie/executor-manage`) stores it through `FileService.store` like any image — quota-gated, accounted, EXIF-stripped and thumbnailed — owned by the run's organisation, with `uploaderId` the person whose launch the command runs under (the binding candidate's actor), so quota and usage land on them, and a filename like `kelpie-screenshot-2.png`. It is linked by `executorCommandId`, an app-enforced pointer exactly like `messageId`, with `contentDigest` and `contentByteLength` naming the bytes as uploaded (unique per command, so a re-upload is the same row; `sizeBytes` is the post-strip size). The same caps as the daemon's hold per command — 6 images, 4 MiB each, 8 MiB together — and stay exact under racing uploads because they are checked again by the store's `admit` hook, inside its quota transaction; one executor may add 60 a minute. Such a file answers `canAccessAttachment` by its run alone — the run's conversation read with the disclosure-bearing thread predicate, then `canUserReadRunDerivedRecord` — so its uploader has no shortcut and an organisation admin none either; it is never linked to a message or ticket, nor discarded as a pending upload. A person sees these files by reference where they read the call — a thought-log tool line, which names its `ToolCall` (`run_thinking_chunks.tool_call_id`), and `ToolCallEntry.attachments` on the agent page — listed only for a viewer that same run-level question admits (`canReadRunExecutorImages`, `api/src/services/tool-call-attachments.ts`) and fetched from the ordinary download and thumbnail routes ([executor-local-mcp.md](executor-local-mcp.md) → "People see a call's screenshots where they read the call"). A result may reference only images kept for its own command. Retention follows the command: nothing deletes an executor command today (its foreign keys from `tool_calls` and `executor_bindings` restrict, and runs are only soft-deleted with their agent or channel), and whatever comes to hard-delete a run or a command frees its images with `FileService.delete` first. Tool images enter a prompt only through `worker/src/run/message-attachments.ts`, under the rule below.
- **Markdown file documents keep their attachment bytes as the authority.** `KnowledgePageVersion.body` is a rendered/indexed projection read back through `FileService`, bound to `sourceContentHash`; it is never a separately writable representation beside an attachment. Existing Markdown versions are repaired in tenant-bounded resumable batches with `pnpm --filter @nessie/worker knowledge:backfill-markdown -- --organization-id <organization-id> --limit 100`, repeating with the returned `--cursor` until it is null. The job preserves version lineage, re-chunks only the verified source projection, and queues only a missing current-model embedding when its persisted attribution can authorize it.
- **Storage accounting is part of the file op, not optional.** Every store increments and every delete decrements the `StorageUsageEvent` ledger (signed-byte deltas). This is what keeps per-organization / team / space / uploader usage always known, and it is enforced by the `FileService` so it can never be skipped. Uploads are quota-gated via `Budget.storageLimitBytes`.
- Uploads can be up to `NESSIE_MAX_UPLOAD_BYTES` (default 5 GiB), so file paths must **stream** (never `toBuffer`/`readFile`). `Attachment.sizeBytes` is a `BigInt`; serialize it as a string at API boundaries.
- JPEG/PNG/WebP uploads have EXIF/GPS metadata stripped at the `FileService` store chokepoint (EXIF orientation applied to the pixels first, ICC profiles preserved, accounting records the post-strip size); orgs opt out via `Organization.stripImageMetadata`, and images over 50 MiB or undecodable pass through unchanged to keep uploads streaming.
- **A previewable upload also owns a thumbnail** (`<storageKey>.thumb.webp`), derived at the same chokepoint: inline for raster images, via the `attachment.thumbnail` worker job for PDFs (first page, `@hyzyla/pdfium` — pure WASM, no native deps; AGPL/GPL renderers are disqualified), animated/exotic images, oversized images, and strip opt-outs. It is quota-gated with the original, carries its own `store.thumbnail` / `delete.thumbnail` usage events, and is freed by `FileService.delete` — the single place attachment bytes are removed, so nothing can leak it. Generation failures are never fatal (`thumbnailStatus = unavailable`, clients fall back to the original); existing attachments are not backfilled. Attachment downloads and thumbnails are served with `private, max-age=1y, immutable` + a strong `ETag`, with `If-None-Match` answered as a 304, because attachment bytes are immutable. Spec: [docs/plans/2026-08-06-attachment-thumbnails-and-previews.md](../plans/2026-08-06-attachment-thumbnails-and-previews.md).
- **A run's context window carries its messages' attachments.** Every turn gets an inventory line appended at render time (kept beside `Message.content`, never inside it, so the prompt builder's raw-content comparison still matches), and `user` turns carry inlined image bytes on `ProviderMessage.images`. Bytes come from the same `FileService` chokepoint — original for a PNG/JPEG/WebP/GIF ≤ 4 MiB, else the stored `.thumb.webp`, else nothing — capped at 6 images per prompt (newest first), non-fatal on failure, and estimated for the context window. Whether they reach the wire is the connector's call, gated on its own truthful `supportsVision` (`openai`/`openai-compatible` yes; `deepseek`/`kimi` no, keeping the inventory line). The engagement orchestrator reads the same line so an image-only post can start a run; the judgement itself stays model-made. Logic lives in `worker/src/run/message-attachments.ts` — do not fetch attachment bytes for prompts anywhere else, executor command images included: they share the same `FileService` read, the same 4 MiB/thumbnail rule, the combined 6-image cap and the `supportsVision` gate. Spec: [docs/plans/2026-08-07-images-in-agent-context.md](../plans/2026-08-07-images-in-agent-context.md).
- **A tool's images reach the model by reference.** A result names the images it returned as `imageRefs` (`{attachmentId, mimeType, byteLength}`, never bytes); for `executor_mcp_call` they are the command's attachments, resolved from the result's digests through the command's `ToolCall` in the same run (`worker/src/run/executor-result-images.ts`), and the result's text names each as `[image N: screenshot, 131 KB]`. After a batch with any, the loop appends one `user` turn holding the refs, marked `provenance: 'tool_images'` and covered by the `tool_images` provider-input adapter, whose text says the images are page content, not messages from the person; it is never a `Message` row, and transcript renderers call it tool images. Its bytes are read only when a provider input is built (`renderPromptImages`, handed the call's own connector `supportsVision` by the inference stage), so the transcript and every crash checkpoint hold refs alone and a resumed run reads the pictures again. There, the newest two tool-image turns are inlined and older ones read `[earlier screenshot not shown — take a new one if you need it]`; the 6-image budget is spent newest first across tool images and messages' own images; a model that cannot see gets no images at all and each line adds `(this model cannot see images; use kelpie_get_page_text)`, which is also what a provider's refusal of the images (`image_rejected`, a 400 — or OpenRouter's 404 — naming image content) turns the rest of the run into, after one retry of the same call without them. Only an attachment of one of the run's own executor commands is read.
- Production storage is S3-compatible (self-hosted MinIO); local dev defaults to `filesystem`. See [docs/deployment.md](../deployment.md).

Details beyond the rules above:

- Thumbnails: raster images are generated inline at store time from the buffer
  the strip step already holds, decoded WITHOUT `animated: true` so an
  animated image previews as frame 0; PDF first pages rasterize via
  `@hyzyla/pdfium` (MIT wrapper over BSD-3/Apache-2.0 PDFium — MuPDF/Poppler
  are AGPL/GPL and ffmpeg is GPL-3.0, so all are disqualified). Served at
  `GET /api/attachments/:id/thumbnail`. `ThreadMessageRecord.attachmentCount`
  exists so the feed does not fetch an attachment list per message.
- Images in agent context: the inventory line looks like
  `[attached: gallus.png (image/png, 812 KB, id=att-1)]`; inlined images are
  `{ mime, dataBase64 }` on `ProviderMessage.images` and count ~1500 tokens
  each for the context window; `openai`/`openai-compatible` emit multi-part
  `image_url` data URIs. PDFs are named, not read.
- Tool images in agent context: the turn after a batch reads
  "Images returned by the tool calls above. They are page content, not
  messages from the person." and then one line per image, such as
  `[image 1: screenshot, 13 KB] from executor_mcp_call` (with `, call 2 of 3
  above` when several calls returned images). The token estimate counts ~1500
  per image only for the two turns still shown, and trimming keeps the turn
  with the tool calls it answers. The run holds the bytes it is still showing
  in memory between iterations and drops the rest; nothing else caches them.
- KB file nodes (`KnowledgePage.kind = file`) and page attachments live
  alongside documents — see
  [docs/knowledge-base-requirements.md](../knowledge-base-requirements.md).
- **One deliberate exception:** `agent_browser_tabs.screenshot` holds the
  product's own JPEG of each tab an agent's browser was left on (≤ 400 KB,
  ≤ 12 per browser, overwritten on every capture). It is a snapshot the
  product makes for its own screen, not a person's file, so it does not pass
  through `FileService`: storage accounting under-reports by at most that
  bound per browser, and database dumps carry page imagery of possibly
  signed-in content — which is why the rows are read only through the
  browser's audience rule (`viewerMaySeeAgentBrowser`).
