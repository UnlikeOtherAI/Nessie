# Read-only channels, mandatory announcements and confirmations

## Outcome

An admin can mark a standard channel read-only. Members can read it; only an organisation owner/admin, or an owner/admin of that channel's team, can post. A second, independent setting marks a public standard channel mandatory. Each eligible admin-authored message then creates a durable in-app alert for every active person in the channel's scope. Push bypasses channel mute and the ordinary-message push preference, while respecting the global push switch, focus mode, quiet hours, operating-system permission and provider availability. The durable alert is the notification guarantee.

In a read-only channel, the admin composer also offers a per-message **Requires confirmation** checkbox, using the same inline checkbox pattern as **Also send to #channel** in the reply composer. When checked, the post shows an **Acknowledge** button. Its message action opens a confirmation-status panel in place of the reply thread: people who acknowledged, people who saw it but have not acknowledged, and people who have not seen it. The original sender can press **Remind unconfirmed**; each currently eligible recipient who has not clicked Acknowledge gets an individual direct message authored by that sender with a link to the exact announcement. Reminders are manual, not scheduled.

A standalone/shared channel addresses the active organisation. A project channel addresses the active members of its exact team. A public project channel may have a wider read audience under today's visibility rules, but its mandatory alert audience does not widen to the whole organisation. A new member receives subsequent announcements, not retroactive alerts. Explicit `ChannelMember` participation still controls the composer; enabling either setting never bulk-joins people. Mandatory recipients can read a public channel without joining it. UOA members who have not signed in to Nessie yet still get a durable subject-keyed entitlement; its bell alert and any requested reminder DM materialise when they first have a local product principal. Device push cannot reach an unregistered device.

## Authority and invariants

- `ChannelMember.role` grants no administrative standing. UOA-bound requests already make a fresh subject-asserted `/org/me` read for the organisation role in `request-admission.ts`. Extend that same response to retain the verified `org.team_roles` map for the duration of the request. Resolve the channel team's exact external id and compare its role to `owner`/`admin`. No paged roster, persistent team-role copy, or fallback to a stale projection is an authority. A UOA refusal is 403; an unavailable verifier is 503 and grants nothing. An install without an IdP uses its local org/team roles.
- Only standard, non-system channels can use either setting. Mandatory **and every confirmation-required post** require public visibility for their full org/team audience. Reject protected/private selection while the mandatory flag or any active confirmation obligation remains. DMs and system channels keep their existing rules.
- Setting changes require org-admin or exact-team-admin standing, distinct from the existing any-member permission to rename or edit a topic. An admin still joins before posting, as management is not participation. Ordinary channel-member management remains unchanged.
- A message's announcement classification and recipient set are fixed at creation. Turning the setting off later does not relabel old alerts. A removed/deactivated recipient is suppressed on later alert reads and push dispatch. A confirmation-required post's content and attachments cannot be edited after sending; edits and direct API replies are refused. Deleting one explicitly cancels outstanding obligations, stops queued reminders and leaves an accessible removed-post tombstone for any already delivered link; it is audited and confirmed in UI. A demoted admin cannot use ordinary edit/delete paths to bypass read-only authority.
- Confirmation is a property of an individual **top-level human admin post** in an active read-only channel, never a channel setting or an agent/system post. A confirmation-required post creates the same scoped durable alert as a mandatory announcement even if the channel's mandatory flag is off; a person cannot be obliged to confirm an undisclosed post. It does not accept replies. Existing non-confirmation messages retain the normal reply action.
- The confirmation audience is frozen with the message. Its per-recipient receipt rows are product-specific extension data (`seenAt`, `acknowledgedAt`, reminder state), keyed by the stable UOA subject for UOA organisations or the local user id for local mode. They store no profile or hierarchy copy. Only currently active members of the original scope count as outstanding or receive reminders; new joiners are not retroactively enrolled. The author is excluded. On first product login, project any subject-keyed pending alert/reminder to the new local principal without an email/name join.
- **Seen** means this client reported that the exact post was visibly displayed, not that a person understood it. The existing `markThreadRead` advances every root in the feed and is therefore not a valid seen signal. A dedicated endpoint accepts a receipt only for its authenticated audience member after exact-message readability checks; the UI calls it after the post is in a foreground viewport. Acknowledging sets `seenAt` too. The panel keeps seen-without-acknowledgment separate rather than treating those people as unseen.
- The receipt roster is visible to the original sender and current org/exact-team admins only. Other recipients see their own state and the Acknowledge button. UOA is queried live for the current role and membership; roster pages are fully traversed and an incomplete/unavailable read fails closed. The mandatory channel shows notifications as always on rather than offering a per-channel mute control; a previously stored mute never suppresses its admin announcements.
- Pending clarification, **leave** means leaving the relevant UOA team or organisation. Leaving the channel's optional `ChannelMember` participation does not opt an active person out of mandatory announcements; otherwise the channel would not reach everyone in scope. An organisation-wide announcement stops for a person who leaves the organisation, and a team announcement stops for a person who leaves that team. Global push and OS controls can still prevent device push; the in-app alert remains the guaranteed notification while the person has access.
- **Existing UOA debt discovered during review:** `User.email`, `displayName` and `avatarUrl` are durable UOA profile mirrors. This conflicts with the supplied UOA authority rule. Do not create one of these rows merely to deliver an announcement, and never use an email join. The API-backed migration is: resolve stable subjects at login; move profile reads to a bounded in-memory UOA relay with revocation-aware freshness; make UOA-owned profile columns nullable; backfill/quarantine ambiguous subject mappings; null existing UOA profile values; add a database check preventing them from being repopulated for UOA principals; retain local-mode fields. This existing migration needs its own impact audit across readers before release, rather than a compatibility copy introduced by announcements.

## Implementation order

1. Add `adminOnlyPosting` and `mandatoryAnnouncements` with false defaults, a new migration, shared channel records, contracts, and audit metadata. Expose server-derived `viewerCanConfigureAnnouncements` and `viewerCanPost` rather than deriving authority from `memberRole` in the client. Channel settings is the owning surface; the composer refusal and notification control are the in-context doorways.
2. Put human posting enforcement in a cohesive posting-policy module because `message-create.ts` already exceeds the repository's 500-line cap. Check the channel setting and live request role at send time, including the ordinary thread route, replies, conversation opening, voice handoff and the PA `send_message` tool. Keep accepted idempotency-key replays as replays. Serialize a setting change against message creation. Use a database insert guard as the final boundary for other `Message.create` paths: a read-only standard room accepts only a transaction carrying verified human-admin authorship. No rejected write may link attachments, create alerts, enqueue jobs or publish realtime events.
3. Classify and handle every non-human write into a standard channel. Agent replies and delegated PA posts are refused as visible posts. Trigger, reminder, workflow, ticket-work, document, mail and other automated kickoffs must be rejected before queueing where possible, with their existing health/delivery surface updated rather than silently lost. Refuse enabling read-only while active agent bindings, trigger targets, workflow installations or writing integrations still target the channel; refuse adding one afterward. A pending run rechecks at execution. System housekeeping notices are not administrator posts and cannot bypass the insert guard. An admin's agent mention in a read-only room must not offer an invitation to an agent that cannot reply.
4. In the human message transaction, enumerate **all pages** of the active UOA organisation/team roster (or local memberships), fail closed on an incomplete read, and freeze stable recipient subjects/ids in a new announcement-delivery table. No local `User` row is fabricated for a member who has not signed in. For recipients with an existing product principal, create one alert row in the same transaction, excluding the author and deduplicating direct mentions. On first login, materialise the subject's pending alert with the original creation time. Use a stable event key per message/recipient. Reuse the existing `mention` enum on persistent and realtime wires for rolling compatibility, but store an immutable announcement marker on the row and expose it through a new *optional* `isAnnouncement` field in `UserAlertRecordSchema` and `alert.created`. The current `metadata` DTO is invitation-only and cannot carry this marker. New clients label the row as an announcement and deep-link to the exact message; old clients may briefly label it a mention but can parse it.
5. Write the announcement's `push.dispatch` outbox job in the **same transaction** as its message and audience; a replay repairs any missing delivery work and cannot double-send. The push recipient set is the persisted announcement-delivery rows with a local registered principal, filtered again through live UOA membership for current exact org/team access. This avoids a new member receiving a push for a message with no delivery row. For mandatory and confirmation-required announcements, bypass channel mute, `pushMessages` **and `pushMentions`** while honoring global push off, focus and quiet hours. Preserve existing per-endpoint send claims, author/channel framing, deep links and private-disclosure checks. Direct mention plus announcement is one alert and one push per recipient.
6. Make the two controls and their permission/explanation states visible in Channel settings; show a read-only explanation in place of a non-admin composer. Explain beside Notifications that mandatory admin announcements still create alerts even when the channel is muted. Update channel, team-model and user-alert documentation. Verify with targeted Turbo suites using a real database, typecheck/build, and a headless Playwright two-user flow and screenshot.
7. Add a strict `requiresConfirmation` send field and immutable message metadata marker, accepted only for a top-level signed-in admin post into a **public** read-only channel. In the same transaction as that post, create the frozen subject-keyed audience receipts, local-principal alerts and push outbox with unique message/recipient keys. Preserve idempotent sends and refuse replies or edits whose root requires confirmation. Old clients ignore the additive metadata; old API replicas must be drained before enabling this control.
8. Add exact-message seen and acknowledge endpoints. Enforce recipient membership, current access, and idempotent monotonic transitions in the database; never accept a client-provided recipient or author. Show the checkbox in the read-only admin composer, the Acknowledge button on required posts, and an accessible confirmation-status panel in the reply doorway's place. Reuse the channel's existing author and identity display patterns without disclosing other tenants' people.
9. Add **Remind unconfirmed** to the original sender's panel only while that sender still has live admin and channel standing. The click records one durable, audited batch as explicit authority for the worker, with one lifetime reminder per message/recipient (retry repairs failed delivery; a later intentional second nudge is a separate future feature). The job stores only the sender's stable subject, product principal and action id; it uses the existing encrypted scoped product link for a fresh UOA `/org/me` check before work, never a copied credential/profile. A revoked epoch, demotion or UOA outage blocks the job with a visible reauthorization/retry state. Each recipient transaction locks its receipt, rechecks current exact-scope membership and `acknowledgedAt IS NULL`, creates the DM message, and writes its push outbox claim atomically. If acknowledgment wins first, no DM is created; if the send wins first, the reminder was valid at its serialized decision point. A standalone announcement's DMs use the organisation's shared-channel root team; a project announcement uses its exact team. Refactor the DM helper for this explicit server-authored, consent-backed send, without pretending the background worker has a live human session. A no-local-principal recipient stays pending until first login. Record failed recipients and offer an honest retry state rather than claiming completion.
10. Test an unseen recipient, a seen-but-unacknowledged recipient, an acknowledged recipient, a private-channel nonmember, a UOA member who never signed in, a removed team member, a newly joined member, author demotion/credential rotation, UOA outage, double click, queue retry, partial fanout failure, post/ack race, edit/delete attempt, direct API tampering, exact deep links and accessible rendered interaction. Both unseen and seen-but-unacknowledged recipients get reminders; acknowledged recipients do not. Keep receipt and reminder detail out of general alert/websocket payloads; use a sender-scoped status event or bounded poll for panel progress, and tell recipients that opening a post reports seen state to admins.

## Acceptance

- A normal member can read a read-only room but has no composer. A direct API post returns 403 with no message, attachment link, alert, job or realtime side effect. This holds for top-level posts, replies, conversation opening, voice handoff and PA `send_message`.
- A team admin may post in their team's room but not another team's; an org admin may post in either after joining. UOA demotion takes effect on the next request; UOA outage returns 503; local mode uses local roles.
- A mandatory standalone admin post alerts all active org members; a mandatory project admin post alerts active exact-team members only. Ordinary member, agent and system posts never produce announcement alerts. Protected/DM/system rooms cannot become mandatory, and a mandatory room cannot become protected.
- A muted recipient and one with `pushMessages: false` receive one alert and one push attempt per registered endpoint. Global push off, focus mode and quiet hours suppress push only. Cross-org, deactivated and removed-team users receive neither. New users after creation do not receive a push without an alert.
- Mention plus announcement, two concurrent posts, idempotent replay and queue redelivery each result in the expected one alert/push per message and recipient. Alerts open the exact message, survive setting changes with the right label, and disappear from a reader who loses access.
- Every automated write site is either unable to target a read-only room or produces a durable health/delivery failure. Adding an agent binding, trigger or workflow target is refused; an already pending run checks again. None silently loses an announcement.
- During a rolling deploy, older API replicas can still accept a post until replaced. Activate the settings only after every API and worker replica runs the guard. The additive alert field keeps old readers parseable during the mixed-version window.
- A confirmation-required announcement renders the inline checkbox on admin send, an Acknowledge button for each eligible recipient, and three honest status groups for the sender. Seen and acknowledgment are monotonic and idempotent; opening the channel without the announcement actually entering the foreground viewport does not mark it seen. The normal reply thread is unavailable for that post, including direct API attempts.
- **Remind unconfirmed** sends one authored DM with an exact link to each currently eligible person who has not clicked Acknowledge at execution, whether seen or unseen. It skips acknowledged, deactivated or removed recipients and never sends twice on retry. The status panel shows sent, pending and failed counts and the sender can retry failures. No user preference is overridden to force delivery of the DM; it uses the ordinary DM notification policy.
