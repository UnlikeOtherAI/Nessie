# Explainability & Accessibility Design

**Date:** 2026-04-07
**Status:** Design

---

## The Problem

Agentic orchestration is powerful but opaque. Systems like OpenClaw are explicitly "for developers." Non-technical users — enterprise staff, managers, customers — cannot use them because they cannot understand or trust them. The system does something invisible and produces a result. If the result is wrong, nobody knows why.

Nessie must be usable by anyone. That means making agents **explainable**, results **trustworthy**, and setup **guided** — without hiding capability from technical users.

The design principle: **confidence through transparency**. Users do not need to understand how agents work. They need to know:
1. The system understood their intent correctly
2. It's doing what it said it would do
3. The result is reliable and they can verify it

---

## 1. Natural Language Workflow Creation

Non-technical users should never have to touch the canvas builder directly unless they want to.

**Flow:**
1. User types: *"Review my PRs and ask the engineering team when there are breaking changes"*
2. System generates the workflow graph from that description
3. Shows a plain-language confirmation: *"Here's what I'll do: 1) Fetch the PR diff when you push. 2) Run your test suite. 3) Review for breaking changes. 4) If found, ask #engineering to approve before merging. Is this right?"*
4. User approves → workflow saved and active
5. Canvas shows the generated graph — user can optionally inspect or tweak

The generated graph is the **confirmation**, not the input. The user wrote one sentence; the canvas is just showing them what was understood.

### Implementation path
- A "Create workflow" chat input on the Workflows page
- The orchestrator interprets the natural language description and calls `create_workflow` with a generated graph JSON
- The canvas renders the result for review
- User can edit node-by-node if needed or just approve as-is

## 2. Three Transparency Layers

Every workflow run and agent action exposes three layers of detail. Users see only what they need; all layers are always accessible.

### Layer 1 — Anyone

Headline status in plain language. No jargon. Traffic light color.

```
✓  PR Review complete — no breaking changes found
⚠  PR Review complete — 2 issues found, team notified
✗  PR Review failed — tests did not pass
⏳ Waiting for approval from #engineering
```

This is the default view. No expand required, no technical terms.

### Layer 2 — Power user

Step-by-step narration of what happened. Plain language, chronological.

```
1. Fetched PR #142 diff — 47 lines changed across 3 files
2. Ran test suite — 12/12 passed (4.2s)
3. Code review — quality score 74/100
4. Eval checked review output — flagged 2 issues
5. Sent approval request to #engineering
```

Visible by expanding a "Show steps" toggle. Each step has a timestamp and duration.

### Layer 3 — Developer

Raw execution log: tool calls, token counts, MCP method, LLM model used, input/output JSON.

```
invoke_workflow  PR-review          inputs: { prId: "142" }
Tool: Bash       pnpm test          exit 0, 4.2s
LLM: gpt-4o      code-review-agent  1,204 tokens
Tool: Bash       git diff HEAD~1    847 chars
MCP: submit_review                  pass=false, issues: [...]
MCP: request_approval               taskId: "abc123"
```

Visible under a "Raw log" toggle. Only relevant to developers debugging a workflow.

## 3. Intent Declaration

Before any agent step executes, the system states its intent in plain language. This is shown in the live run view.

```
About to run:  Code Reviewer — checking for breaking API changes
Reason:        Tests passed. Moving to code quality check.

[ Stop ]  [ Continue ]
```

This is not a prompt for approval (that is the Human Input node). This is a **narrated preview** — it shows what is about to happen and why. Users can stop it. If the stated intent is wrong, they catch it before execution.

Non-technical users read this the same way they read a progress indicator — it tells them the system is behaving as expected.

### Surfacing reasoning

After each agent step, the result includes a plain-language "Why?" summary generated by the LLM:

> *"I flagged the `updateUser` function because it does not validate the `email` parameter before passing it to the database query. If the API returns null, this will throw an unhandled exception in production. The existing tests do not cover this case."*

This is distinct from the raw LLM output. It is a generated summary — 2–4 sentences, no code unless necessary, no jargon. Technical users can still click through to the full reasoning.

## 4. Eval Transparency

Evals are an Agent node + Router combo (no special node type — see workflow builder doc). But their output should be presented distinctly.

### What to show

Instead of pass/fail, show a structured trust summary:

```
┌─────────────────────────────────────────┐
│  Eval result                            │
│                                         │
│  Quality score:   87 / 100              │
│  Criteria:        Accuracy ✓            │
│                   Completeness ✓        │
│                   Safety ✓              │
│                   Edge cases ✗          │
│                                         │
│  Finding: Missing null check on line 42 │
│  Finding: No error message for 403      │
│                                         │
│  [ Show full reasoning ]                │
└─────────────────────────────────────────┘
```

The criteria checked, the score, and the specific findings are all surfaced directly. Non-technical users see "87/100, two things to fix." Developers click "Show full reasoning" to see the full LLM output.

### Eval criteria come from the workflow

When building the workflow, the Eval Agent node has a "What to check" field — a plain-language list of criteria:
- "Did the agent answer the user's actual question?"
- "Are there any security issues in the code changes?"
- "Is the response factually accurate?"

These criteria appear in the result view so users can see exactly what was evaluated.

## 5. Template Library

Non-technical users should not start from a blank canvas. The Workflows page includes a template library of pre-built common patterns:

| Template | Description |
|----------|-------------|
| PR Review | Fetch diff → run tests → code review → eval → team approval |
| Content Approval | Draft content → eval for accuracy/tone → human review → publish |
| Support Ticket Triage | Classify ticket → route to right team → notify assignee |
| Daily Briefing | Gather sources → summarise → send to channel |
| Data Report | Query data → analyse → format report → deliver |
| Incident Response | Detect alert → diagnose → escalate → notify on-call |
| Onboarding Flow | New member → provision access → notify team → schedule intro |

Each template is a fully wired workflow graph. The user selects it, fills in a few blanks (which channel, which repo, etc.), and it is live.

Templates lower the entry point from "understand agents" to "fill in this form."

## 6. Guided Agent Creation

Creating an agent should be conversational, not form-filling.

Instead of a blank form with fields for system prompt, model, and tool checkboxes, the agent creation page starts with a conversation:

```
Tell me about this agent.
What should it do? Who is it for?

> It should monitor our support inbox and flag anything urgent to the on-call team.

Got it. A few questions:
- What counts as urgent? (keywords, sentiment, both?)
- Who is the on-call team? (channel or specific people?)
- How often should it check? (real-time, every hour, daily?)
```

The system extracts the specification from the conversation and shows a preview of the generated agent config. The user reviews and approves.

The form still exists and is accessible — advanced users go directly to the canvas and fields. But the conversational entry path means anyone can create an agent without knowing what a "system prompt" is.

## 7. Status Language

Every system state must have a plain-language label. No internal status codes in the user-facing interface.

| Internal status | User-facing label |
|-----------------|-------------------|
| `waiting_for_input` | "Waiting for your response" |
| `awaiting_approval` | "Waiting for team approval" |
| `in_progress` | "Running" |
| `review` | "Being reviewed" |
| `failed` | "Something went wrong" |
| `done` | "Complete" |
| `cancelled` | "Stopped" |

Error messages must include:
1. What happened (plain language)
2. Why it happened (if known)
3. What to do next (actionable)

Never show raw error codes or stack traces in the user-facing layer. Raw errors are available in Layer 3 for developers.

---

## 8. Trust Signals

Every completed workflow run and agent action should carry visible trust signals:

- **Eval score** — if an eval ran, show the score badge on the result
- **Human reviewed** — if a Human Input node was involved, show who reviewed it and when
- **Sources cited** — if the agent used external data, list the sources
- **Confidence indicator** — if the agent flagged uncertainty, surface it ("I'm not fully confident in this answer — you may want to verify")
- **Audit trail** — every result links to a full, immutable record of what happened

These signals give non-technical users a framework for deciding when to trust the output and when to double-check.

---

## 9. Implementation Notes

These features layer onto the existing workflow and agent infrastructure:

- **Natural language creation**: orchestrator interprets description → calls `create_workflow` with generated graph
- **Intent declaration**: each workflow node emits `node.intent` event before execution (new event type)
- **Why? summary**: after each agent step, the LLM generates a 2–4 sentence plain-language summary stored in the workflow run log
- **Eval formatting**: structured output schema for eval agents (`{ passed, score, criteria, findings }`)
- **Template library**: stored as pre-seeded workflow records in the DB
- **Status labels**: a mapping layer in the UI between internal status enums and display strings
- **Trust signals**: surfaced from existing task reviews, approval records, and run metadata

None of these require new backend primitives. They are presentation and narration layers over what the system already produces.
