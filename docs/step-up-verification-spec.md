# Step-Up Verification Add-On

> Status: target-state design.

## 1) Objective

Provide a reusable verification layer that can be attached to any high-risk action.

The add-on must support:
- email code verification,
- link-based confirmation pages,
- QR-based authenticator enrollment,
- time-based one-time passwords (TOTP),
- future factor types without changing the action model.

This is a transport-agnostic security layer. It is not limited to deployment flows.

## 2) When to require it

Use step-up verification for:
- deployments,
- secret rotation or export,
- new email recipients or outbound notification jobs,
- destructive project actions,
- privileged tool use,
- agent or channel membership changes,
- any action that policy marks as “high risk”.

## 3) Factor model

Supported factor types:
- `email_otp`: one-time code sent to a verified email address.
- `email_link`: one-time confirmation link that returns to a confirmation page.
- `totp`: time-based code generated by an authenticator app.
- `recovery_code`: fallback code for account or factor recovery.
- `webauthn`: reserved for future phishing-resistant factors.

Rules:
- factor enrollment must be explicit,
- factor use must be scoped to an actor and target action,
- factor data must never be stored in chat or prompts,
- expired or reused challenges must fail closed.

## 4) Email verification flow

Email verification is a step-up factor for task approval and external send actions.

Flow:
1. User or agent requests a high-risk action.
2. System sends a one-time code to a verified email address.
3. User enters the code or follows a confirmation link.
4. Confirmation page returns a signed approval proof.
5. The protected action proceeds only after proof is attached to the control action envelope.

The same flow applies when an agent needs to unlock a secret-backed action:
- the agent requests the challenge,
- the user receives the code or link,
- verification completes before `secret.resolve` is allowed.

Constraints:
- codes are short-lived,
- codes are single-use,
- resend must be rate limited,
- verification must fail if the email address is unverified or no longer in policy scope.

## 5) Authenticator enrollment flow

TOTP enrollment must support QR-based setup for common authenticator apps, including Google Authenticator and Microsoft Authenticator.

Flow:
1. User requests factor enrollment.
2. System generates a TOTP secret and provisioning URI.
3. UI renders a QR code from the provisioning URI.
4. User scans the QR code in an authenticator app.
5. User confirms enrollment by entering a current code.
6. The enrolled factor becomes available for future step-up checks.

Rules:
- the TOTP secret must be stored as a secret reference, not in chat,
- the QR payload is a transient representation of the secret,
- enrollment requires an explicit confirmation step,
- recovery codes should be shown once and then stored hashed.

## 6) Action binding

Step-up verification attaches to a control action, not to a single product feature.

Examples:
- `deploy.project` may require `totp` plus `email_otp`,
- `tool.invoke` may require `email_link` for first-time use,
- `secret.rotate` may require `totp` and a recovery-code fallback path,
- `secret.resolve` may require `email_otp`, `email_link`, or `totp` before a secure API key can be used,
- `mail.send` may require `email_otp` before an external recipient is added.

The binding must support:
- `anyOf` and `allOf` factor sets,
- required factor counts,
- TTL on approvals,
- explicit reason codes when verification fails.

Scope resolution:
- `VerificationPolicy.scope` defines the maximum boundary where the factor policy applies.
- A challenge must carry concrete target IDs that are equal to or narrower than that scope.
- Example:
  - `scope: 'project'` may authorize a project-level or channel-level action inside that project,
  - `scope: 'team'` requires `teamId` and may also include `channelId`,
  - a challenge that cannot be anchored to the declared scope must fail closed.

## 7) Data model

```ts
type VerificationPolicy = {
  policyId: string;
  actionIds: string[];
  requiredFactors: Array<{
    factorType: 'email_otp' | 'email_link' | 'totp' | 'recovery_code' | 'webauthn';
    count: number;
  }>;
  challengeTtlMs: number;
  resendCooldownMs: number;
  maxAttempts: number;
  scope: 'organization' | 'project' | 'team' | 'channel' | 'agent' | 'user' | 'service';
};

type VerificationChallenge = {
  challengeId: string;
  policyId: string;
  actorId: string;
  actorType: 'user' | 'agent' | 'service';
  organizationId: string;
  projectId?: string;
  teamId?: string;
  channelId?: string;
  targetActionId: string;
  approvalId?: string;
  factorType: 'email_otp' | 'email_link' | 'totp' | 'recovery_code' | 'webauthn';
  status: 'pending' | 'verified' | 'expired' | 'cancelled' | 'failed';
  expiresAt: string;
  proof?: string;
};

type VerificationEnrollment = {
  factorId: string;
  factorType: 'email_otp' | 'email_link' | 'totp' | 'recovery_code' | 'webauthn';
  ownerId: string;
  secretRef?: string; // required for TOTP/recovery material
  label: string;
  verifiedAt?: string;
  revokedAt?: string;
};
```

## 8) API contracts

Required actions:
- `verification.challenge.start`
- `verification.challenge.verify`
- `verification.challenge.resend`
- `verification.challenge.cancel`
- `verification.factor.enroll`
- `verification.factor.verify`
- `verification.factor.revoke`
- `verification.factor.list`

Suggested HTTP contracts:
- `POST /verification/challenges`
- `POST /verification/challenges/{challengeId}/verify`
- `POST /verification/challenges/{challengeId}/resend`
- `DELETE /verification/challenges/{challengeId}`
- `POST /verification/factors`
- `POST /verification/factors/{factorId}/verify`
- `DELETE /verification/factors/{factorId}`
- `GET /verification/factors`

WebAuthn note:
- `webauthn` remains a reserved factor type in the shared policy model.
- Dedicated WebAuthn registration/assertion endpoints are intentionally not part of the first implementation pass.

## 9) UI requirements

- Email verification must show a code-entry view and a link-based confirmation page.
- Authenticator enrollment must render a QR code.
- High-risk actions must surface the required factor types before execution.
- Failure states must be explicit, not silent.

## 10) Security requirements

- step-up proof must be attached to the action envelope and audit trail,
- codes must not be persisted in chat or logs,
- factor enrollment secrets must use `secretRef` storage,
- replayed challenges must be rejected,
- factor policy must be transferable across projects, teams, channels, agents, and tools.
